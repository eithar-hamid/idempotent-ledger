# idempotent-ledger

[![CI](https://github.com/eithar-hamid/idempotent-ledger/actions/workflows/ci.yml/badge.svg)](https://github.com/eithar-hamid/idempotent-ledger/actions/workflows/ci.yml)

A double-entry ledger service in **Java 17 and Spring Boot 4** where money can't move twice. Retries can't do it, duplicate requests can't, and neither can two requests racing each other.

It's a small, self-contained demonstration of the patterns payment and wallet systems depend on, backed by tests that **fail when the protection is removed**.

## The problem

A client sends "transfer 100 AED". The network times out. Did it go through? The client can't tell, so it retries. Meanwhile a second device sends the same request, and another transfer debits the same account at the same moment.

A naive implementation now has three ways to lose or invent money:

| Failure | Naive behaviour | This service |
|---|---|---|
| **Retry after a timeout** | Applies the transfer again | Returns the original result (`200`, `Idempotent-Replayed: true`) |
| **Same key, different payload** (a client bug) | Applies the new payload | Rejects it with `409 Conflict` |
| **Concurrent debits** on one account | Read-then-write race, so the balance goes negative | A single guarded `UPDATE`, so it never overdraws |
| **Opposite transfers** A→B and B→A at once | Database deadlock, so one request fails | Rows are locked in a fixed order, so there's no deadlock |
| **Partial failure** mid-transfer | One side updated, the other not | One transaction: all lines or none |

## How it works

```
POST /transfers   Idempotency-Key: order-42
        │
        ▼
1. INSERT journal_entry (idempotency_key, request_hash) ON CONFLICT DO NOTHING
        │
        ├── 0 rows → key already exists ──► same hash?  yes → return stored entry (200, replayed)
        │                                               no  → 409 Conflict
        ▼ 1 row
2. UPDATE account SET balance = balance + delta
     WHERE id = ? AND currency = ? AND (allow_negative OR balance + delta >= 0)
   … for each account, in account-id order
        │
        ├── 0 rows → 404 / 400 / 422, whole transaction rolls back (key released)
        ▼
3. INSERT ledger_line × 2   (amounts sum to zero)
        │
        ▼
   COMMIT → 201 Created
```

### Design decisions

- **Insert-first idempotency.** The idempotency key is claimed by the *first* write, against a unique constraint. A "check, then insert" approach has a window where two requests both see "not found". Here, if a second request with the same key arrives while the first is still in flight, PostgreSQL blocks it on the unique index until the first commits or rolls back. Only one can ever apply.
- **Request fingerprint.** The key is stored with a SHA-256 hash of the request. Reusing a key with a different amount or account is a client bug, and it's rejected instead of being silently treated as a replay.
- **Failed requests release the key.** If a transfer fails (for example, insufficient funds), the key claim rolls back with it, so the client can top up and retry with the same key. *Trade-off:* the alternative, which stores failures and replays them, is stricter but forces clients to mint a new key after fixing the cause.
- **Guarded atomic updates, not read-modify-write.** The balance check lives in the `WHERE` clause of the `UPDATE`, so there's no gap between reading and writing for a second transaction to slip into. A `CHECK` constraint on the table is a second line of defence.
- **Fixed lock order.** Accounts are always updated in ascending id order. Two opposite transfers can't each hold one row while waiting for the other's.
- **Minor units as `BIGINT`.** Amounts are integers (fils, cents), never floating point.
- **Plain SQL with `JdbcClient`.** The correctness properties live in specific SQL statements, so they're written out explicitly rather than generated by an ORM.
- **Self-checking.** `GET /ledger/integrity` verifies that every account balance equals the sum of its lines and every journal entry sums to zero. The test suite runs the same checks after every test.

## Proving it: the tests

Integration tests run against real PostgreSQL via **Testcontainers**, with no mocks of the database, because the guarantees *are* database behaviour.

| Test | What it proves |
|---|---|
| `retryWithSameKeyReturnsOriginalResultAndMovesNothing` | A retry is a no-op that returns the original entry |
| `sameKeyWithDifferentRequestIsRejected` | Key reuse with a new payload → conflict, nothing applied |
| `failedTransferReleasesKeySoTheClientCanRetry` | A failure rolls back the key claim |
| `concurrentDebitsNeverOverdraw` | 20 simultaneous debits of 10 against a balance of 100 → exactly 10 succeed, balance ends at 0 |
| `concurrentRetriesOfOneKeyApplyExactlyOnce` | 10 simultaneous copies of one request → applied once, all 10 get the same entry |
| `oppositeTransfersDoNotDeadlock` | 40 simultaneous A→B / B→A transfers all complete |
| `TransferApiTest` | The HTTP contract: `201` / `200 + Idempotent-Replayed` / `409` / `422` / `400` |

**The tests catch the bugs they claim to.** Removing the account-id sort from `TransferService` makes `oppositeTransfersDoNotDeadlock` fail with PostgreSQL's `deadlock detected` (3 of 3 runs).

## Run it

Requirements: JDK 17+ and Docker.

```bash
./mvnw test                                   # full suite, starts PostgreSQL in a container

docker compose up -d                          # PostgreSQL on localhost:5432
./mvnw spring-boot:run                        # API on http://localhost:8080
```

Or run against a throwaway Testcontainers database with no compose: start `TestIdempotentLedgerApplication` from your IDE.

### Try it

```bash
# Accounts: an external funding account (may go negative) and a customer
curl -s -X POST localhost:8080/accounts -H 'Content-Type: application/json' \
  -d '{"name":"Funding","currency":"AED","allowNegative":true}'
curl -s -X POST localhost:8080/accounts -H 'Content-Type: application/json' \
  -d '{"name":"Alice","currency":"AED"}'

# Transfer. Run it twice: the second response is 200 with Idempotent-Replayed: true
curl -si -X POST localhost:8080/transfers -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-42' \
  -d '{"fromAccountId":"<funding-id>","toAccountId":"<alice-id>","amountMinor":10000,"currency":"AED"}'

curl -s localhost:8080/accounts/<alice-id>
curl -s localhost:8080/accounts/<alice-id>/lines
curl -s localhost:8080/ledger/integrity
```

## API

| Method | Path | Notes |
|---|---|---|
| `POST` | `/accounts` | `{name, currency, allowNegative}` → `201` |
| `GET` | `/accounts/{id}` | Balance in minor units |
| `GET` | `/accounts/{id}/lines?limit=50` | Most recent ledger lines |
| `POST` | `/transfers` | Header `Idempotency-Key` (required, ≤ 100 chars). `201` applied · `200` replayed · `400` invalid · `404` unknown account · `409` key reused · `422` insufficient funds |
| `GET` | `/ledger/integrity` | Consistency self-check |

Errors are [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details.

## Out of scope (on purpose)

Authentication, multi-currency FX, entries with more than two lines, holds and authorisations, key expiry, and event publishing (a Transactional Outbox would be the next step). The project is kept small so its core guarantees are easy to read and verify.
